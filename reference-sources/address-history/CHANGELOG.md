## v4.5 — 列名归一化识别 + 多 key 默认 + 一键脚本默认开高德核验(2026-06-09)

同事用「AI 通话记录导出」表试跑时,字段名是 `地址1/省1/市1/区\县1/姓名1`(带数字后缀+反斜杠),
`[ERR] 找不到地址列` 直接中止、整表无法处理。排查 + 修复 + 增强:

- **列名归一化兜底**(`fused_validate._colmap` + 新增 `_norm_header`):
  匹配前先归一化表头(去末尾数字、`\`→`/`、全角括号→半角),
  让 `地址1→地址 / 省1→省 / 市1→市 / 区\县1→区/县 / 姓名1→姓名` 都能识别;
  精确匹配仍优先,**标准表零影响**。`name` 别名调序(姓名 先于 客户名称),
  优先取与地址同源的结构化「姓名1」。
- **高德多 key 默认轮询**:内置 `DEFAULT_AMAP_KEYS`(7 个 key),`--amap-keys` 默认即用之;
  全量存在性核验 5320 行从"数分钟"降到 **~50s**(QPS≈21)。
- **一键脚本默认升级**(`run_validator.command`):默认 `--amap-scope all --verify-existence`,
  同事双击即"离线 R1–R9 + 高德全行兜底 + 可发货行存在性核验",备注写 `[地图]…`;
  简洁版《快速上手.txt》同步说明已联网核验(可加 `--amap-scope none` 回纯离线)。
- 实测(5320 行,AI 通话导出):可发货 70.7%→**73.9%**、待人工 27.7%→24.2%、
  逆地理纠/补乡镇 **1467 条**、地图核到 3190/3934(81%)、存疑 744 已标注。
- **自治区省名修正**(`verify_addresses.py`):`广西→广西省` 改为 `广西→广西壮族自治区`,
  并兜底被错写成"X省"的 5 自治区(广西省/内蒙古省/宁夏省/新疆省/西藏省 → 全称);
  `广西/广西省` 统一规范为「广西壮族自治区」。`lookup_county` 的 `hint_province` 匹配会
  剥省/自治区后缀两边比对,故省内查县/冲突判定不受影响。

## v4.1 — 输入读取层加固(2026-06-03)

同事试用反馈"输出比输入少了 10 条",排查后定位为**读取层**两个问题,均已修复并回归。

### 排查过程(逐步定位)
1. 按地址字符串对比:发现输出 < 输入,但数字对不上(假象,被格式差异放大)。
2. 改用稳定主键比对 + 量化三处行数:
   - `openpyxl 活动表`非空行 = **3985**
   - 脚本实际用的 `read_sheet`(读第一个 sheet)= **3998**
   - 输出 = **3988**
   - → `read_sheet − 输出 = 10`,锁定丢行发生在**处理循环**。
3. 进一步发现 `read_sheet` 读的表头与用户看到的**完全不同**:工作簿有 3 张表
   (`元数据 / 脚本处理数据 / 处理好数据`),脚本**固定读第一个**,而用户在看另一张。

### 修复
- **不再静默丢行**(`fused_validate.py` 解析循环):
  - 删除 `if not addr: continue`;地址列为空时用 `省+市+区县` 兜底,强标「待人工」并在备注注明;
  - 只跳过"整行全空";极端全空也保留(合成最小记录,不崩);
  - 启动打印 `待处理: N 条 (地址列为空但已保留 X 条, 跳过整行全空 Y 条)`。
- **多 sheet 选表**(`fused_validate.py` 读取层):
  - 默认改读「活动表」(`wb.active`),不再固定第一个;
  - 新增 `--sheet "表名"` 显式指定(不存在则告警回退);
  - 启动打印 `工作簿含 N 张表 / 实际读取「表名」/ 读入 M 行 + 表头`,杜绝"读错表不自知"。

### 回归
- 用 `--sheet "元数据"` 重跑:`读入 3998 → 完成 3998`,**行数对齐,不再少 10 条**;
  其中"地址列为空已保留 10 条"全部落在「待人工」并带兜底备注。
- 分档:可发货 2999(75%,含已纠正 285)/ 待人工 971(24%)/ 无效 28;MD5 解密 3994/3997。

### 文档
- `使用说明.txt` / `README.md` / `SOP_地址校验全流程.md` 均加「多 sheet 选表 + 行数守恒」说明;
- SOP 新增 §0.5「输入读取层」;bad case 台账记两条(静默丢行 P0、读错表 P1)为已修复。
