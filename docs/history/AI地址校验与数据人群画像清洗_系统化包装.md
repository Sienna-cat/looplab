# AI 营销协作系统：地址校验与数据人群画像清洗

## 一句话定位

我没有把 AI 当成单点提效工具，而是把两个高频、强规则、容易出错的营销环节重构成可复用的协作系统：**触达前用数据人群画像清洗与策略泛化回答“应该优先触达谁”，触达后用 AI 地址校验回答“哪些订单可以进入履约”。**

这套方法的主线是：**发现系统性问题 → 重构人机流程 → 把经验变成 Agent 能力 → 用评测决定自动化和扩量 → 沉淀成团队可复用资产。**

> 口径说明：地址模块聚焦地址信息校核与人工分流；人群模块聚焦客户标识、漏斗标签和客群规则的清洗与迁移验证。两者都不是“生成训练数据”的项目。历史结果、正式评测设计和本地模拟 Demo 分开展示。

# 01｜AI Address Verification Agent

## 地址校验｜履约前地址核验流程智能化重构

**副标题：从“清洗一列地址”，到“让每笔订单都能基于证据决定放行、补采或转人工”。**

### 1. 背景：问题不是地址格式，而是履约决策没有证据链

原流程通常是：

> 读取订单表 → 提取地址文本 → 省市区匹配 → 尝试纠错 → 标记状态 → 交给发货或人工

真正影响业务的痛点有四个：

1. **原始信息容易被覆盖。** 一旦把模型或规则改写后的地址直接写回，后续无法判断系统改错了什么。
2. **“能匹配”不等于“可以发货”。** 地图返回候选、同音地名或行政区命中，只能说明存在可能性，不能直接当作客户最终确认。
3. **异常被压成一个状态。** 缺门牌、客户改地址、录音与表格冲突、工具失败，需要不同的业务动作。
4. **批处理可能静默漏单。** 空地址、错误工作表、重复订单和输出错位，数量看似一致也可能造成履约风险。

一句话问题定义：**如何在控制错误放行风险的前提下，让更多订单安全地减少人工流程？**

### 2. 我的思考：AI 是核验协作者，不是“自动改地址”的脚本

**Before：规则驱动全部流程**

订单表 → 自动解析 → 自动纠错 → 输出“可发货 / 待人工”

**After：确定性校验 + AI 组织证据 + 人工确认**

订单输入 → 保留原始值 → 字段与行政区校验 → 生成候选 → 展示通话 / 地图 / 规则依据 → 按风险分流 → 人工裁决 → 回写结果与 Bad Case

我的产品判断是：

- 规则负责字段完整性、订单标识、行政区层级和放行条件；
- AI 负责理解上下文、组织核验步骤、解释候选差异；
- 人工负责证据不足、多个候选和客户最终确认；
- 所有修改都要留下原值、候选值、依据、动作和版本。

因此产品目标从“改出一个看起来标准的地址”变成“让核单人员能快速作出可追溯的履约决策”。

### 3. Agent 能力模型：按核单决策链路拆分能力

| Agent 模块 | 输入 | 判断 / 动作 | 输出 |
| --- | --- | --- | --- |
| 订单完整性 Agent | 订单 ID、原始地址、表格结构 | 检查空值、重复 ID、工作表和行数守恒 | 可处理记录、异常记录、导入错误 |
| 地址结构 Agent | 原始地址、省市区、ASR 文本 | 拆分省 / 市 / 区县 / 街道 / 门牌，识别缺失字段 | 结构化字段及缺失项 |
| 行政区校验 Agent | 结构化字段、行政区划库 | 检查层级冲突、直辖市、省直辖县和同名地区 | 校验结果与冲突原因 |
| 候选与证据 Agent | 原文、音近词、候选地址、地图或录音证据 | 生成候选并说明来源，不把相似度当成真值 | 原始值、候选值、差异和证据链 |
| 风险分流 Agent | 校验结果、证据完整度、工具状态 | 判断自动通过、补采、重试或转人工 | 下一步动作、风险等级和阻断原因 |
| 人工裁决 Agent | 原始记录、候选、证据、历史处理 | 支持确认、修改、驳回和写入原因 | 最终状态、裁决人、版本和 Bad Case |

### 4. 训练 Agent：把“核单经验”变成可执行规则

这里的训练不是简单调 Prompt，而是把核单人员的隐性判断拆成规则、证据和动作。

#### Step 1：把模糊判断改写成业务规则

- “这个地址不完整” → 缺少可履约定位所需的字段，不能自动放行；
- “这个地名可能写错了” → 保留客户原话，列出候选和差异，证据不足则补采；
- “地图上能搜到” → 只能作为候选证据，不能代替客户确认；
- “这一行有问题” → 记录具体原因：空地址、层级冲突、工具失败、跨订单错位或需要补录。

#### Step 2：建立地址核验知识与状态字典

沉淀行政区层级、同音 / 近音词、可接受的标准表达、异常原因、状态映射和人工动作。统一历史版本中“可发货、待抽查、待人工、无效”等不同表达，避免跨版本比较时分母发生变化。

#### Step 3：按版本迭代协作方式

- **V1：批量规则处理。** 能完成字段匹配和基础分流，但容易覆盖原文，异常原因不够清楚。
- **V2：证据优先。** 固定输出原始地址、候选地址、差异、证据和不确定性；空地址保留并转人工。
- **V3：任务型 Agent。** 将重试、补采、人工裁决、回写和 Bad Case 纳入状态机，形成可追踪的核单队列。

### 5. 评测：先控制错误放行，再讨论自动化比例

#### 已有历史证据

对历史输出 `测试_1645.csv` 逐行复核得到：

| 统计项 | 结果 | 能说明什么 |
| --- | ---: | --- |
| 输出记录 | 3,985 条 | 该批输出的处理规模 |
| 工具判为可发货 | 2,936 条 / 73.68% | 分流比例，不是地址准确率 |
| 待人工 | 1,014 条 / 25.45% | 人工复核负载 |
| 地址冲突 | 35 条 / 0.88% | 工具判定的冲突状态，不等于客户无效 |
| 标记已纠正 | 39 条 / 0.98% | 发生过修改，不等于修改全部正确 |

这组数据支持“已经形成批量处理、结果分流和异常追溯机制”，不能直接写成“准确率 73.68%”或“人工减少 73.68%”。

#### 正式评测协议

1. 以客户、订单和重复录音聚类，建立开发集、冻结测试集和挑战集；
2. 由两名核单人员独立标注可接受地址、是否允许自动放行、缺失信息和必须转人工原因，再对分歧仲裁；
3. 冻结规则、行政区库、词典、ASR 和外部工具版本；
4. 测试集发现的问题进入下一轮开发，原测试集转为回归集，不继续声称是新的独立验收集。

#### 核心指标

| 指标 | 定义 | 对应产品判断 |
| --- | --- | --- |
| 自动放行错误率 | 不应自动放行的记录数 ÷ 被评审的自动通过记录数 | 能不能安全放行 |
| 问题订单拦截召回率 | 被拦截的问题订单数 ÷ 真值要求人工 / 补采的订单数 | 有没有漏掉高风险订单 |
| 自动通过覆盖率 | 自动通过数 ÷ 全部有效输入数 | 能减少多少人工 |
| 纠错精确率 | 改对的记录数 ÷ 全部修改记录数 | 自动修改是否可靠 |
| 正确地址误改率 | 原本正确但被改错数 ÷ 原本正确地址数 | 是否因为纠错制造新错误 |
| 行数与 ID 守恒 | 输出 ID 集合与输入 ID 集合逐项比对 | 是否漏单、重单或串字段 |
| 人工总耗时 / 单笔成本 | 复核、补采、修改和重试耗时与成本 ÷ 输入数 | 是否真正产生业务价值 |

#### 本地 Demo 验证

LoopLab 使用 24 条虚构地址挑战案例覆盖 15 类问题，独立保存示例真值；支持原始值、候选值、证据、处理轨迹、人工裁决和 JSON 导出，16 项核心测试通过。该 Demo 验证的是流程、状态和评测逻辑，未接入生产 ASR、地图或订单系统。

### 6. 结果价值：从“处理地址”升级为“守住履约质量”

- **效率价值：**将简单、证据充分的记录交给规则自动处理，把人工时间集中到缺失、冲突和工具失败的记录。
- **质量价值：**原始值、候选值和证据同时保留，避免自动纠错把错误带入履约。
- **组织价值：**把核单人员的判断转成状态字典、放行规则、挑战集和 Bad Case 回归机制，新人可以沿用同一套标准。
- **角色价值：**产品经理从“写地址清洗脚本需求”升级为“设计可解释、可追责的人机核验系统”。

### 7. 可放进简历的一句话

> 将地址清洗任务重构为证据优先的 AI 核单流程，定义原始值保留、候选地址、风险分流、人工裁决及 Bad Case 回归机制；复核 3,985 条历史输出并建立自动放行错误率、问题拦截召回率、纠错精确率和人工负载等评测口径，借助 Demo 验证 15 类挑战场景与 16 项核心测试。

# 02｜AI Audience Intelligence Agent

## 数据人群画像清洗｜营销客群策略与泛化验证智能化重构

**副标题：从“清理数据、挑高转化维度”，到“让客群规则在新客户、新时间和新号段上可验证、可解释、可复用”。**

### 1. 背景：问题不是做不出画像，而是画像很难迁移到下一批客户

原流程通常是：

> 汇总全量号码和订单 → 去重 / 清洗 → 按省份、运营商、号段等维度切分 → 计算出单表现 → 选高转化人群 → 交给外呼或投放

真正的系统性问题有五个：

1. **同一客户可能出现多行。** 不先按客户标识去重，策略会被高频记录客户放大。
2. **标签和观察窗口不统一。** 触达前可知信息与触达后结果混在一起，容易把未来信息泄漏进策略。
3. **样本内高分不等于可扩量。** 细分越多，越容易得到偶然的高转化组合。
4. **覆盖率与效果没有一起决策。** 小客群可以有高 Lift，却无法支撑实际预算和外呼容量。
5. **画像结果难以复用。** 一次性分析报告没有规则版本、适用范围和失效条件，下一批客户还要重新人工解释。

一句话问题定义：**如何把一次性的客户分析，变成可在新样本、新时间批次和新号段上复现的客群策略？**

### 2. 我的思考：AI 是策略分析协作者，不是“自动找最高转化率”的脚本

**Before：分析师驱动全部流程**

全量数据 → 手工清洗 → 试很多维度 → 挑最高转化组合 → 直接扩量

**After：数据契约 + 规则候选 + 留出验证 + 业务取舍**

数据口径检查 → 客户去重 → 漏斗标签与成熟窗口 → 生成候选画像规则 → 训练集建规则 → 验证集选维度与阈值 → 冻结后测试 → 根据 Lift、覆盖率、稳定性和成本决定观察、试投或扩量

我的产品判断是：

- 数据清洗和分母口径由确定性逻辑保证；
- AI 负责将业务问题转成候选维度、解释规则和提示风险；
- 验证集负责选方案，最终测试集只负责验收；
- 运营人员看到的不只是“高分人群”，还包括样本数、覆盖规模、历史衰减、未知组合和适用边界。

### 3. Agent 能力模型：按“从画像到策略”的决策链路拆分能力

| Agent 模块 | 输入 | 判断 / 动作 | 输出 |
| --- | --- | --- | --- |
| 数据契约 Agent | 客户 ID、时间、来源、漏斗字段、结果成熟窗口 | 检查必需字段、时间关系、重复和缺失 | 数据质量报告与不可用记录 |
| 客户归一 Agent | 原始号码 / 客户标识及多行记录 | 去重、聚合同一客户、固定归属集合 | 唯一客户数据集与切分清单 |
| 漏斗标签 Agent | 接通、意向、出单、签收等事件 | 统一标签定义，区分特征与结果 | 可追溯漏斗标签与分母 |
| 画像候选 Agent | 省份、运营商、号段世代等触达前特征 | 生成单维 / 二维 / 三维候选规则，应用最小样本门槛 | 候选规则、样本数和覆盖率 |
| 泛化评测 Agent | 训练 / 验证 / 测试集合 | 计算 Lift、绝对转化率、衰减、未知组和区间 | 版本化评测报告 |
| 策略建议 Agent | 评测结果、预算和外呼容量 | 在效果与规模之间给出观察、试投或扩量建议 | 可执行客群策略与适用范围 |

### 4. 训练 Agent：把“会看画像”变成可复用的规则资产

#### Step 1：把经验判断转成可执行规则

- “这个维度太细了” → 设定最小样本量，并要求在验证集复现；
- “这个人群看起来很准” → 同时查看绝对出单率、事件数和入选覆盖率；
- “下一批也应该有效” → 必须通过客户分组、时间外或新号段留出验证；
- “数据太脏了” → 明确重复 ID、标签冲突、结果未成熟和未知组合的处理方式。

#### Step 2：建立画像知识库和口径字典

沉淀客户唯一标识、去重逻辑、触达前特征、订单 / 签收观察窗口、样本门槛、Lift、覆盖率、衰减和未知组的定义。每条规则记录来源字段、版本、计算集合和可扩量边界。

#### Step 3：按版本迭代策略生产方式

- **V1：样本内画像分析。** 生成维度分组和高转化排序，但容易把偶然高分当成扩量依据。
- **V2：唯一标识与留出验证。** 按客户去重并隔离训练、验证和留出数据，比较效果、覆盖率和衰减。
- **V3：策略评测 Agent。** 先冻结规则，再测新时间 / 新号段，输出观察、试投和扩量建议，并记录重复使用测试集的探索标记。

### 5. 评测：先证明规则能迁移，再讨论要不要扩大人群

#### 已有历史证据

唯一客户标识复核口径记录：9,199,438 个唯一 ID，匹配出单 ID 4,216 个。历史候选排序使用过留出表现，因此这组结果适合作为方案比较和产品取舍依据，不能直接当作最终独立测试集。

| 规则 | 训练 Lift | 留出 Lift | 留出覆盖率 | 相对衰减 |
| --- | ---: | ---: | ---: | ---: |
| 归属地省 × 运营商 | 1.56 | **1.27** | 15.78% | -18.51% |
| 归属地省 × 运营商 × 号段世代 | 1.66 | **1.17** | 21.76% | -29.62% |

这个结果带来的产品判断是：三维规则训练表现更高、覆盖更多，但留出 Lift 更低、衰减更大；二维规则更稳，三维规则可以作为扩量候选，但需要同预算 / 同覆盖比较和新的独立验证。

`Lift 1.27` 表示入选客群出单率约为同一留出集整体出单率的 1.27 倍，不等于出单率 27%，也不等于线上带来 27% 的因果增量。

#### 正式评测协议

1. 只使用触达当时已知的特征，固定出单、签收等结果的成熟窗口；
2. 同一客户只进入一个集合，先按客户去重，再进行开发、验证和最终测试切分；
3. 在开发集生成规则，在验证集选择维度、最小样本量和入选阈值；
4. 冻结后只用最终测试集验收，不根据测试结果反向改规则；
5. 另建时间外测试和新号段整组留出，分别回答未来批次和未见号段能否迁移；
6. 线上用客户级随机试点，在相同预算、容量、话术和核单政策下比较现行策略与新策略。

#### 核心指标

| 指标 | 定义 | 对应产品判断 |
| --- | --- | --- |
| 最终测试 Lift | 入选客群出单率 ÷ 同测试集整体出单率 | 是否仍有富集效果 |
| 绝对出单率与事件数 | 同时报告真实比例、出单数和样本数 | 高 Lift 是否来自极小样本 |
| 入选覆盖率 | 被策略选中的客户数 ÷ 评测入口客户数 | 是否能支撑实际规模 |
| 可评估覆盖率 | 满足最小样本门槛的客户数 ÷ 入口客户数 | 规则能覆盖多少可判断人群 |
| 留出衰减 | 留出 Lift ÷ 训练 Lift - 1 | 是否存在过拟合风险 |
| 未知组占比 | 测试中无法应用既有规则的客户数 ÷ 入口客户数 | 扩量时会损失多少覆盖 |
| 固定预算有效订单与成本 | 同资源投入下有效订单、签收和总成本 | 是否值得上线或扩量 |

#### 对比基线

至少比较现行业务策略、同预算随机选择、简单单维规则、二维规则和三维规则；在相同预算或相同覆盖下观察效果，避免只选最小且最漂亮的人群。

### 6. 结果价值：从“做一份画像报告”升级为“建设策略生产系统”

- **效率价值：**把客户归一、漏斗口径、维度候选、留出验证和报告生成变成可复用流程，减少每次从头解释数据。
- **质量价值：**把客户去重、标签成熟、数据泄漏、样本不足和过拟合风险写进评测协议，让“高分”必须同时经得起迁移验证。
- **组织价值：**沉淀客群规则、版本、适用范围、失败条件和 Bad Case，新成员可以复用同一套策略资产。
- **角色价值：**从“帮运营跑画像分析”升级为“设计能评测、能试投、能复盘的营销策略系统”。

### 7. 可放进简历的一句话

> 将客户画像清洗重构为可迁移的客群策略评测流程，统一客户去重、漏斗标签、样本门槛和训练 / 验证 / 测试口径；复核二维与三维规则的 Lift、覆盖率和衰减，识别“三维训练更高但留出 Lift 由 1.27 降至 1.17”的稳定性取舍，并设计时间外、新号段及固定预算试点验证路径。

# 03｜两个模块如何组成一套 AI 协作系统

## 共同的产品主线

| 阶段 | AI 人群画像清洗 | AI 地址校验 | 共同资产 |
| --- | --- | --- | --- |
| 业务问题 | 触达前不知道优先投谁 | 转化后不知道订单能否履约 | 把局部任务改成可执行决策 |
| Agent 角色 | 组织数据、生成候选规则、解释泛化结果 | 组织证据、判断风险、触发人工动作 | AI 负责理解和编排，确定性逻辑守住边界 |
| 人工角色 | 选择预算、确认策略、决定试投 / 扩量 | 裁决冲突、补采信息、确认最终地址 | 人工掌握关键决策与异常接续 |
| 评测问题 | 新样本能否复现 | 自动放行是否安全 | 评测决定自动化程度 |
| 反馈回流 | 新批次结果、未知组、策略失效 | Bad Case、人工裁决、履约失败 | 反馈进入规则、提示和评测集 |

## 这套方法体现的产品能力

1. **先定义决策，再定义 AI。** 不从“能不能接模型”出发，而从“谁要做什么决定”出发。
2. **把经验写成输入、输出、状态和动作。** 让 Skill 可以被别人使用、复盘和验收。
3. **把评测放进产品流程。** 核单先看错误放行风险，人群先看样本外稳定性，再谈自动化和扩量。
4. **把 Bad Case 变成组织资产。** 每次错误都进入原因字典、回归案例和版本记录。
5. **把设计师 / 产品经理角色往上提。** 从执行一个任务，升级为设计一套 AI 协作系统和业务反馈闭环。

**副标题：从单点数据清洗，到可评测、可追溯、可复用的 AI 协作系统**

## 面试两分钟总述

我把两个看似分散的任务放回同一条营销链路：触达前要判断哪些客户值得优先投入，触达后要判断采集到的地址能不能安全进入履约。过去这两个环节容易被理解成数据清洗和脚本处理，但真正的问题是决策没有被标准化，经验也没有被沉淀成可复用能力。

所以我把 AI 定位为协作系统的一部分。人群画像模块负责客户归一、漏斗口径、候选规则和样本外验证；地址模块负责原始信息保留、候选地址、证据组织、风险分流和人工裁决。AI 负责理解和编排，确定性逻辑负责边界，人工负责关键判断。

评测上，我没有把地址分流比例写成准确率，也没有把历史留出 Lift 写成线上因果提升。地址看错误放行、问题拦截、纠错精确率和人工负载；人群看 Lift、覆盖率、衰减、未知组和固定预算成本。两个模块分别验收后，再用有效签收订单和总成本判断整个营销链路是否值得放量。

这体现的是我从“会用 AI”到“能设计 AI 协作系统”的能力：发现系统性问题，拆解人机边界，把隐性经验变成 Skill 和评测协议，再把 Bad Case 变成团队可复用的产品资产。

## 简历上可用的三条合并版

- **营销链路重构：**将客户画像清洗与地址校验组织为“客群策略—营销触达—地址核验—履约反馈”协作链路，定义输入输出、版本、证据、异常状态和人工动作。
- **评测体系：**为地址模块建立错误放行、拦截召回、纠错精确率、行数守恒和人工负载口径；为客群模块建立客户去重、三集合隔离、Lift、覆盖率、衰减、时间外 / 新号段验证口径。
- **产品价值：**把一次性数据处理升级为可复用 Skill 和 Bad Case 回归机制，让评测决定哪些环节自动化、哪些需要人工、哪些策略可以试投或扩量。
